# ManClient: pilot runbook

## 1. Что разворачивается

- один Next.js web/worker image;
- PostgreSQL 16 как источник истины;
- приватный S3-compatible bucket для чеков;
- HTTPS endpoints для Telegram и WhatsApp webhooks;
- планировщик фоновых задач внутри того же образа, внешний cron не нужен (раздел 7).

Владелец бизнеса регистрируется сам на `/register` и завершает настройку в кабинете (раздел 4). Оператор ManClient нужен только для поддержки, восстановления и смены тарифа.

## 2. Обязательные переменные

Скопируйте имена из `.env.example`. В production secret manager должны находиться:

- `DATABASE_URL`, `DATABASE_DIRECT_URL`;
- `AUTH_SECRET`, `CARD_ENCRYPTION_KEY`, `INTEGRATION_ENCRYPTION_KEY`, `INTERNAL_API_SECRET`, `BOOKING_ACTION_SECRET`, `PLATFORM_LINK_SECRET`;
- S3 credentials;
- platform bot credentials: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET`;
- `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`.

Опционально, но по каждой есть отдельный раздел ниже: `PAYOM_PHONE_VERIFICATION_TEMPLATE_ID` и `PHONE_VERIFICATION_REQUIRED` (подтверждение номера и восстановление пароля), `PLATFORM_ADMIN_ALERT_CHAT_ID` (алерты об ошибках), `PLATFORM_PAYMENT_CARD` (оплата подписки, раздел 7.1), `LOG_LEVEL`.

`APP_URL` и `AUTH_URL` должны указывать на публичный HTTPS origin. `TELEGRAM_BOT_USERNAME` задаётся без `@`. Не используйте значения из тестов или `.env.example`.

Генерация ключей:

```bash
openssl rand -base64 32   # CARD_ENCRYPTION_KEY и INTEGRATION_ENCRYPTION_KEY
openssl rand -hex 32      # остальные HMAC/session secrets
```

## 3. Database и storage

```bash
pnpm prisma migrate deploy
pnpm prisma migrate status
```

Создайте приватный bucket из `S3_BUCKET`. Public read запрещён. Включите server-side encryption, versioning и lifecycle хранения по согласованному сроку.

Backup PostgreSQL:

```bash
pg_dump --format=custom --no-owner "$DATABASE_URL" > manclient-$(date +%F).dump
pg_restore --clean --if-exists --no-owner --dbname "$DATABASE_URL" manclient-YYYY-MM-DD.dump
```

Restore сначала проверяется на отдельной БД. `--clean` нельзя направлять на production без отдельного подтверждения.

## 4. Первый бизнес

Владелец регистрируется на сайте и завершает настройку в кабинете. Оператор ManClient подключается только при поддержке или восстановлении. Для каждого бизнеса:

1. В `Филиалы` проверьте адрес, телефон, timezone и состояние филиала.
2. В `Команда` создайте специалистов и назначьте их на филиалы.
3. В `Ресурсы` добавьте кабинеты, кресла, боксы или оборудование, если они ограничивают одновременную запись.
4. В `Услуги` задайте цену, длительность, специалиста и ресурс, затем опубликуйте услугу.
5. В `Расписание` проверьте рабочую неделю, перерывы и ближайшие исключения. Личный график специалиста перекрывает график филиала.
6. В onboarding сохраните карту. Номер шифруется приложением; plaintext не сохраняется и не логируется.
7. Откройте `/b/<business-slug>` и выполните тестовую запись на минимальную согласованную сумму.

Demo seed создаёт `demo-barber` и `demo-auto` только для локальной/CI проверки. Не запускайте demo seed в production.

## 4.1. Правила записи

`Настройки → Правила записи` задают четыре числа, которые продукт применяет, а не просто показывает:

- **минимальный запас до записи** — за сколько клиент обязан записаться (0 = сразу);
- **горизонт записи** — на сколько дней вперёд открыт календарь (пусто = без ограничения);
- **окно отмены и переноса** — до какого момента клиент меняет визит сам (0 = в любое время);
- **лимит переносов** одной записи клиентом (пусто = без лимита).

Значения по умолчанию соответствуют поведению до появления раздела, поэтому существующие бизнесы после обновления работают ровно так же. Правила действуют на публичной странице, в клиентском Telegram-боте и на публичных ссылках отмены/переноса; сотрудники в кабинете ими не ограничены — администратор всегда может записать клиента «на сейчас» и перенести визит за час до него.

Клиенту правила показываются на `/b/<slug>` рассчитанными строками рядом со свободным текстом из поля «Текст правил». Отказ клиенту всегда называет причину: «не позднее чем за N ч», «переносили N раз».

Серии повторяющихся записей проверяются по правилам только на первом визите: горизонт в 90 дней иначе обрубал бы 12-недельную серию, которую бизнес включил намеренно.

### Предоплата и депозиты

Новый салон заводится **без предоплаты** (`prepaymentMode = NONE`): просить незнакомого человека перевести полную стоимость до первой стрижки — самое жёсткое, что этот продукт умеет требовать, и это должно быть решением салона, а не наследством. Раньше по умолчанию стояло `FULL` — просто потому, что так работали все бизнесы до появления депозитов. **Существующие салоны сохраняют свой режим**, миграция меняет только значение по умолчанию для новых.

Из этого следует ещё одно: шаг «Куда принимать оплату» в онбординге по-прежнему обязателен, хотя новому салону карта сразу не нужна. Она понадобится в тот момент, когда он переключится на депозит или полную оплату, — но сделать этот шаг необязательным стоит отдельно.

`Настройки → Правила записи → Предоплата` решает, сколько денег должно прийти до визита:

- **полная стоимость** — поведение до появления настройки: бронь висит 15 минут и ждёт чек на всю сумму;
- **депозит** — процент (округляется вверх до целых сомони) или фиксированная сумма; остаток бизнес получает на месте;
- **ничего** — запись подтверждается сразу, оплата на месте.

Запрос, в котором поля предоплаты нет вовсе, режим не меняет: сохранение правил, которое ничего не говорит про деньги, — это сохранение правил о времени. Раньше отсутствующее поле означало «поставить полную предоплату», то есть самый жёсткий режим мог включиться от того, что его не прислали.

Депозит без указанной суммы сохранить нельзя: недоделанная настройка списывала бы полную стоимость. Отдельная услуга может переопределить правило бизнеса (`Настройки → Услуги → Предоплата этой услуги`) — дорогая окраска требует депозит, подравнивание чёлки нет. Пустое поле у услуги означает «как у бизнеса».

Что меняется технически: `Payment.amountDiram` — это сумма, которую попросили сейчас (по ней сверяется чек), `Payment.totalDiram` — стоимость визита; разница собирается на месте и видна в карточке записи. При правиле «ничего» платёж создаётся со статусом `NOT_REQUIRED` и суммой 0, бронь сразу `CONFIRMED` без срока истечения, и напоминания с подтверждением уходят так же, как после принятого чека. Карта получателя обязательна только когда деньги действительно запрашиваются, поэтому бизнес с оплатой на месте может её не настраивать.

### Неявки

Карточка подтверждённой записи, время которой уже прошло, показывает «Отметить неявку». Это не отмена: слот никто не освобождал, специалист ждал. Запись переходит в `NO_SHOW`, запланированные напоминания и запрос отзыва становятся `SKIPPED`, счётчик неявок клиента растёт (виден в `Клиенты`), а уже полученная предоплата помечается `Payment.forfeitedAt` — это то, ради чего депозит и берут. В календаре дня неявка остаётся на своём месте зачёркнутой: час был потрачен.

**Буферы услуги** (`Настройки → Услуги`) — подготовка до и уборка после визита. Время занимает специалиста и ресурс, но клиенту не показывается и не оплачивается. Максимум 4 часа на каждую сторону: на эту величину расширяется запрос занятости, больший буфер просто не был бы учтён при проверке пересечений. Буферы физические, поэтому действуют и на записи из кабинета.

## 5. Telegram platform и клиентские боты

`TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и `TELEGRAM_WEBHOOK_SECRET` принадлежат только общему бизнес-ассистенту `@manclient_bot`. В `@BotFather` включите для него Bot Management Mode. Бизнес не создаёт отдельного административного бота: владелец и команда привязывают Telegram-аккаунты к готовому `@manclient_bot`.

Каждый бизнес создаёт только одного собственного бота — клиентского. Основной flow использует Telegram Managed Bots: владелец подтверждает создание в Telegram, сразу получает ownership, а `@manclient_bot` получает token через Bot API и сохраняет его зашифрованно с `INTEGRATION_ENCRYPTION_KEY`. Токены клиентских ботов не добавляются в environment.

После deploy зарегистрируйте platform webhook и native-команды `/start`, `/menu`, `/today`, `/bookings`, `/checks`, `/help`. Скрипт не выводит token или secret:

```bash
pnpm telegram:register-platform-webhook -- --dry-run
pnpm telegram:register-platform-webhook
```

Целевой URL: `https://<host>/api/webhooks/telegram/platform`. Endpoint принимает запрос только с совпадающим `X-Telegram-Bot-Api-Secret-Token`. Старый `/api/webhooks/telegram` после cutover обязан отвечать `410 Gone`.

Проверка без вывода credentials — `pnpm probe:https` (см. §9). Если проверяете вручную, legacy endpoint нужно дёргать именно POST: на GET route отвечает `405`, а `410 Gone` возвращает только POST.

```bash
curl --fail --silent --show-error "$APP_URL/api/health"
curl --silent --output /dev/null --write-out '%{http_code}\n' -X POST "$APP_URL/api/webhooks/telegram"
```

Ожидается `200` для health и `410` для legacy webhook.

### Подключение tenant bot

1. Владелец или администратор открывает `Настройки -> Интеграции`, нажимает `Создать клиентского бота` и переходит в общий `@manclient_bot`.
2. После привязки бизнеса нажимает одноимённую кнопку. Telegram показывает нативное окно создания; ownership сразу принадлежит Telegram-аккаунту владельца.
3. Platform webhook получает update `managed_bot`, вызывает `getManagedBotToken`, проверяет точный bot ID и регистрирует уникальный webhook `/api/webhooks/telegram/business/<publicId>`.
4. Если бизнес уже владеет ботом, используйте вторичное действие `Подключить существующего бота` и вставьте token в кабинете. Не отправляйте token в чаты.
5. Отправьте `/start` в клиентский бот и проверьте выбор языка, филиала и услуги.
6. Проверьте `/bookings`: клиент видит только свои записи в этом бизнесе, может нативно перенести или отменить будущий визит.
7. Откройте payment deep link, нажмите «Я оплатил» и отправьте чек. Чек обязан изменять только выбранный `paymentId`, даже если у клиента несколько ожидающих оплат.

При ротации сначала регистрируется новый webhook. Если Telegram недоступен, старый бот остаётся активным. Отключение удаляет webhook и зашифрованные credentials, но не удаляет самого бота в Telegram.

После регистрации проверьте:

1. Public booking показывает ссылку tenant bot, а не `@manclient_bot`.
2. `/start` в platform bot показывает бизнес-ассистента; подписанная ссылка из кабинета привязывает бизнес-чат и истекает через 15 минут.
3. `/today`, `/bookings` и `/checks` показывают только бизнес и роль подключённого сотрудника; STAFF не видит чужие записи и чеки.
4. Новая запись, чек, решение по оплате, перенос и отмена появляются в бизнес-ассистенте через durable outbox. Ошибка Telegram не откатывает запись.
5. Изображение чека сохраняется в private bucket.
6. Matching receipt подтверждает запись; сомнительный попадает в `NEEDS_ATTENTION`.
7. Кнопки переноса и отмены не содержат raw booking ID без подписи.

### Rollback Telegram cutover

Код и миграции additive (добавляют таблицы и индексы), поэтому rollback приложения не требует отката схемы. Перед rollback сохраните backup, разверните предыдущий проверенный image/SHA и верните platform webhook на поддерживаемый этим SHA endpoint. Не удаляйте новые таблицы в incident: это необратимо уничтожит tenant integrations и conversation state.

Если потерян `INTEGRATION_ENCRYPTION_KEY`, tenant bot tokens восстановить нельзя. Верните ключ из secret-manager backup или переподключите каждого бота новым token через кабинет. Ротация этого ключа требует отдельной транзакционной утилиты; простая замена environment сломает расшифровку существующих integrations.

## 6. WhatsApp Cloud API

Укажите Graph API version через `WHATSAPP_GRAPH_API_VERSION`. В `WHATSAPP_TEMPLATE_ALLOWLIST` перечислите только одобренные Meta templates. На Business задаются phone number ID, confirmation template, reminder template и language code.

Webhook URL: `https://<host>/api/webhooks/whatsapp`. GET challenge проверяет `WHATSAPP_VERIFY_TOKEN`; POST delivery updates проверяет `X-Hub-Signature-256` через `WHATSAPP_APP_SECRET`.

## 7. Jobs

В Docker-образе планировщик (`src/jobs/scheduler.ts`) запускается автоматически вместе с сервером (см. `CMD` в `Dockerfile`) и раз в минуту вызывает expiry, reminders, receipt-processing, business-notifications, integration-health-alerts и security-maintenance, а раз в час — data-retention и subscription-lifecycle. Отдельный cron не нужен.

Каждая задача выполняется под advisory lock PostgreSQL (`manclient:job:<name>`). Это делает безопасными rolling deploy с двумя живыми контейнерами и ручной запуск рядом с работающим планировщиком: второй процесс видит занятый lock и тихо пропускает задачу. Упавшая задача уходит в exponential backoff от 1 до 15 минут, а не повторяется каждую минуту. На `SIGTERM` планировщик ждёт до 30 секунд завершения текущих задач.

Список задач один и тот же для планировщика и для CLI (`src/jobs/job-registry.ts`), поэтому cron-развёртывание не может «потерять» задачу:

```bash
pnpm jobs:expire
pnpm jobs:reminders
pnpm jobs:receipts
pnpm jobs:business-notifications
pnpm jobs:subscriptions
# или все сразу в непрерывном режиме, как в контейнере:
pnpm jobs:scheduler
```

Delivery имеет claim state и максимум три попытки. В `Message.lastError` пишется ответ провайдера для SMS и WhatsApp (например, отклонённый payom-шаблон); для Telegram остаётся обобщённый текст, так как bot token передаётся в URL запроса — подробности уходят только в лог.

### Лестница каналов

Одно событие — одно сообщение, по самому дешёвому каналу, который его вытянет: **Telegram → WhatsApp → SMS** (`src/core/notifications/channel-ladder.ts`). Раньше каждое событие рассылалось по всем доступным каналам сразу: клиент с Telegram получал ещё и WhatsApp, и SMS за 0,045 сомони — за новость, которую уже прочитал.

Канал выбирается при планировании, но это только начало пути. Если канал оказался тупиком — у салона отключён бот, нет одобренного шаблона, три попытки подряд не прошли, — задача доставки пишет **новую строку `Message` на следующий канал вниз**, а прежняя остаётся со статусом `SKIPPED`/`FAILED` и причиной в `lastError`. То есть по строкам видно, что пробовали и почему спустились. В логах это `message.handed_down` (с полями `from` и `to`) и `message.ladder_exhausted`, когда ниже уже некуда.

Что важно для разбора жалоб «мне ничего не пришло»: смотреть надо **все** строки по `bookingId`, а не первую — их теперь может быть несколько, по одной на испробованный канал.

Доступность канала считается из настроек: Telegram — есть ли `Customer.telegramChatId`; WhatsApp — есть ли `whatsappPhoneNumberId` и одобренный шаблон именно под этот вид сообщения; SMS — включён ли тумблер салона, входит ли SMS в тариф и есть ли payom-шаблон. Вид сообщения без шаблона (например, просьба об отзыве) на платные каналы не уходит вовсе.

Push встанет над Telegram, когда появится мобильное приложение: это одна строка в массиве `CHANNEL_LADDER` и один отправитель в `src/core/notifications/senders/`.

## 7.0. Бэкапы и ретеншн

Бэкап Postgres — расписание в Coolify на базе `manclient-postgres`: ежедневно в 03:00, 7 локальных копий (`0 3 * * *`, `save_s3: false`). Локальные копии лежат на том же сервере, поэтому это защита от ошибочного удаления, а не от потери сервера: выгрузку в S3 нужно включить отдельно, когда появится Coolify S3 storage.

Задача `data-retention` (раз в час) удаляет то, что перестало быть свидетельством: идентификаторы вебхуков Telegram старше 30 дней, просроченные callback-токены старше 7 дней, отправленные и отброшенные сообщения и уведомления бизнесу старше 180 дней. Не удаляет **никогда**: платежи, чеки и их файлы в S3, аудит, записи и клиентов — это ответ на вопрос «что произошло с чужими деньгами», и его рост нужно решать сознательно, а не побочным эффектом уборки. Максимум 5000 строк на таблицу за прогон, чтобы уборка не держала блокировки.

## 7.1. Жизненный цикл подписки

Задача `subscription-lifecycle` (раз в час) двигает подписки по сроку: `TRIALING`/`ACTIVE` с прошедшим `subscriptionEndsAt` уходят в `GRACE`, а `GRACE` старше семи дней — в `EXPIRED`. `GRACE` намеренно ничего не отключает: это предупреждение, а не наказание. Гасит платные функции только `EXPIRED`, и гасит именно их — записи, клиенты, история и публичная страница `/b/<slug>` работают всегда.

`subscriptionEndsAt = null` не трогается никогда. Это и бизнесы, заведённые до биллинга, и ручной грант платформенного админа — «без срока» здесь означает буквально без срока.

Бизнес получает уведомление в свой Telegram за три дня до конца периода, в момент перехода в `GRACE` и в момент `EXPIRED`. Ключ дедупликации содержит дату конца периода, поэтому перезапуск задачи в ту же минуту молчит, а продление срока после оплаты снова включает предупреждения — уже про новый период.

Новый бизнес при регистрации получает `PREMIUM` в статусе `TRIALING` на 14 дней (`TRIAL_DAYS` в `src/core/platform/subscription-lifecycle.ts`).

### Тарифы и счета

Цена задаётся в бэкофисе, `Платформа → Тарифы`, парой «тариф + период»; продаются только `Стандарт` и `Премиум`, `Старт` бесплатен и цены не имеет. Пустое поле означает, что тариф не продаётся: подписки на нём продолжают работать, но счёт по нему не выставляется. Каждое изменение цены попадает в журнал как `platform.plan_price.changed` или `platform.plan_price.cleared` — это события платформы, без бизнеса в колонке «Бизнес» там стоит «Платформа».

Счёт хранит сумму слепком, а не ссылкой на прайс: изменение цены завтра не меняет того, что бизнес должен сегодня. Второй открытый счёт не создаётся — запрос возвращает уже выставленный, чтобы к одной подписке не пришлось сопоставлять два перевода.

Чек за подписку бизнес присылает из кабинета; файл проходит тот же контроль, что и клиентские чеки — JPEG/PNG/WebP, до 10 МБ, проверка декодированием, случайный ключ хранения, — и попадает в `subscriptions/<businessId>/<invoiceId>/`. Оплата засчитывается автоматически, только если сходятся все пять признаков: в чеке написано «успешно», сумма равна счёту, перевод ушёл на карту платформы, а время операции не раньше выставления счёта и не в будущем. Иначе чек уходит в очередь `Платформа → Подписки`, а счёт получает статус `NEEDS_ATTENTION`.

Номер операции уникален по всем чекам за подписку: один и тот же скриншот не купит второй месяц ни тому же бизнесу, ни другому. Пока `PLATFORM_PAYMENT_CARD` пуста, сверять не с чем — такие чеки всегда идут к оператору.

Решение оператора: подтверждение продлевает период через `extendPeriod` (оплата заранее сохраняет неиспользованные дни, оплата спустя месяцы не выкупает молчавшие) и пишет `subscription.paid`; отказ требует причины, возвращает счёт в `OPEN` — бизнес может прислать другой чек — и пишет `subscription.receipt_rejected`. Изображение чека отдаётся только через `/api/platform/subscriptions/<id>/receipt` под сессией админа платформы, бакет остаётся приватным.

`PLATFORM_PAYMENT_CARD` — карта платформы, только цифры, нигде не хранится и в базу не попадает. Пока переменная пуста, бизнес не видит ссылку на оплату, а в кабинете написано, что оплату принимает оператор; счёт при этом выставить можно.

### Спорная оплата

Порядок, когда бизнес говорит «я оплатил», а подписка этого не видит:

1. `Платформа → Подписки` — очередь чеков, которые не сошлись автоматически. В строке видно ожидаемую сумму, сумму из чека, последние цифры карты и причину.
2. Откройте само изображение (ссылка «Открыть»): OCR ошибается на плохих фотографиях, и глазами видно то, чего не увидела программа.
3. Сходится — «Подтвердить оплату»: счёт становится `PAID`, период продлевается, в журнале бизнеса появляется `subscription.paid`. Не сходится — «Отклонить» с причиной: счёт возвращается в `OPEN`, бизнес может прислать другой чек, в журнале появляется `subscription.receipt_rejected`.
4. Если чека нет вовсе, а деньги пришли (перевод сделали мимо ссылки, чек потерян), выдайте срок вручную — см. ниже. Счёт при этом остаётся открытым; закройте его отклонением с причиной «оплата зачтена вручную», чтобы бизнес не платил дважды.

Ни один из этих путей не называется банковски подтверждённым: мы читаем чек, а не выписку. В аудите это записано явным `isBankVerified: false`.

### Ручной срок

`Платформа → Бизнесы → <бизнес> → Тариф`: тариф и поле «Оплачено по». Пустая дата означает бессрочный доступ — ровно то же, что `subscriptionEndsAt = null` в базе: задача жизненного цикла такие подписки не трогает никогда, и именно так выглядят бизнесы, заведённые до биллинга.

Сохранение всегда возвращает статус `активна`, то есть снимает `GRACE` или `EXPIRED`. Иначе грант не имел бы смысла: тариф был бы выдан, а платные функции остались бы выключенными, потому что право считается по статусу, а не по одному тарифу. Дата в прошлом допустима — часовая задача на следующем проходе честно уведёт подписку обратно в `GRACE`.

Каждое такое изменение пишется в журнал как `business.plan_changed` со старым и новым тарифом, прежним статусом и обеими датами.

### Материалы для салона

`Настройки → Материалы` в кабинете: QR-код на публичную страницу салона и четыре макета под печать — наклейка на зеркало 100×100 мм, настольная табличка A6, плакат на дверь A5 и визитка 90×50. Размер кода на каждом подобран под расстояние чтения, коррекция ошибок максимальная, код чёрный на белом: цветной код дешёвые камеры читают плохо, и отказ этот молчаливый — клиент просто уходит.

Рядом с кодом на всех макетах напечатан человекочитаемый адрес: когда код затрут или заклеят, клиент наберёт его руками. Ничего устаревающего — цен, акций, имён мастеров — на макетах нет намеренно: салон печатает их один раз и оставляет на год.

Из этого следует эксплуатационное требование: **`APP_URL` и slug бизнеса менять нельзя после того, как макеты напечатаны.** Смена домена обнуляет все наклейки в городе. Если slug всё же меняется, старый адрес обязан отвечать вечным редиректом.

## 7.2. Логи, метрики и алерты

Приложение и планировщик пишут по одному JSON-объекту на строку в stdout. Уровень задаётся `LOG_LEVEL` (`debug|info|warn|error`, по умолчанию `info`). Значения секретов из окружения и bot token вырезаются из сообщений и stack trace автоматически, номера телефонов маскируются до последних четырёх цифр.

Необработанные ошибки любого route, server action и RSC перехватываются в `src/instrumentation.ts`. Если задан `PLATFORM_ADMIN_ALERT_CHAT_ID`, о них и о задачах, исчерпавших попытки, приходит алерт в личный чат админа с `@manclient_bot`. Одинаковые ошибки не дублируются в течение часа.

Метрики Prometheus:

```bash
curl -sS -H "x-manclient-internal-secret: $INTERNAL_API_SECRET" https://<host>/api/internal/metrics
```

Что смотреть в первую очередь: `manclient_customer_message_backlog_age_seconds` и `manclient_business_notification_backlog_age_seconds`. Значение, превышающее несколько минут, означает, что планировщик не работает, — по глубине очереди это выглядит как обычный тихий вечер. Дополнительно: `manclient_customer_messages{status="FAILED"}`, `manclient_receipt_submissions`, `manclient_telegram_integrations{status="ERROR"}`.

### Пять метрик пилота

Очередные метрики выше говорят, работает ли машина. Эти пять — работает ли бизнес под ней. Отдаются тем же endpoint'ом.

| Метрика | Вопрос, на который отвечает | Что считать тревогой |
| --- | --- | --- |
| `manclient_sms_sent_30d{businessId,purpose}` и `manclient_sms_cost_diram_30d{businessId}` | сколько стоит салон в единственной переменной себестоимости | рост SMS при неизменном числе записей — лестница каналов перестала спасать; `purpose="VERIFICATION"` заметно больше числа доведённых записей — коды жгут деньги впустую |
| `manclient_customers{businessId,telegram}` | сколько вообще может унести бесплатный канал | доля `telegram="yes"` ниже трети — SMS будет основным каналом, и это надо закладывать в цену |
| `manclient_subscription_receipts_30d{status}` и `manclient_subscription_review_minutes` | цена ручного биллинга и когда он упрётся | доля `NEEDS_REVIEW` выше половины либо среднее время разбора растёт — оператор перестаёт успевать |
| `manclient_active_businesses_7d` | кто ещё жив | падение при неизменном `manclient_businesses{state="registered"}` — отток начнётся через 3–6 недель, до первой неоплаты |
| `manclient_businesses{state}` и `manclient_customers_90d{kind}` | инструмент или маркетплейс | `ever_paid` не растёт вслед за `registered`; `returned` сильно ниже `booked` — клиенты не возвращаются, значит салон покупает записи, а не инструмент |

**Цена SMS.** `manclient_sms_cost_diram_30d` считает по `SMS_PRICE_DIRAM` (по умолчанию `4.5`, то есть 0,045 сомони — подтверждённый тариф payom на 14.08.2026). При смене тарифа достаточно задать переменную, деплой не нужен.

**Почему одна строка журнала равна одному списанию.** Платит payom за **сегмент**, а не за отправку: в детализации рядом с каждым сообщением стоит «Кол-во сообщений» и списание кратно ему. Кириллическая SMS — это UCS-2, 70 символов на сегмент; сообщение длиннее уходит двумя и стоит вдвое.

Поэтому название салона обрезается под бюджет **конкретного шаблона**: `buildPayomVariables` считает, сколько от 70 символов осталось после одобренного текста, даты и времени, и укорачивает `text-1` до этого. Бюджеты разные — от 22 символов у таджикского подтверждения записи до 41 у русского напоминания, — поэтому одной константой тут не обойтись: она либо резала бы лишнее, либо не спасала. Обрезанное имя всё равно говорит клиенту, кто пишет; двойной счёт не говорит ничего.

Следствие: каждое сообщение гарантированно в один сегмент, значит число строк в `SmsCharge` равно числу списаний **по построению**, а не по оценке. Если появится шаблон с более длинным текстом, проверка `tests/unit/notifications/sms-segment-budget.test.ts` уронит сборку до того, как счёт вырастет вдвое.

**Откуда берутся SMS.** Из `SmsCharge` — отдельного журнала, по строке на каждое сообщение, за которое заплатили. Ни одна из существующих таблиц на этот вопрос не отвечает: `Message` держит одну строку независимо от числа попыток, дошедших до шлюза, а `PhoneVerification` удаляется через сутки после смерти кода, потому что хранить хеш кода, который уже никто не предъявит, — чистая ответственность без пользы. В журнале нет ни телефона, ни хеша — только чей был расход и когда, поэтому его можно хранить столько, сколько нужно бухгалтерии.

Записывается ровно там, где сообщение уходит: нижняя ступень лестницы каналов и отправка кода. Строка появляется **после** того, как шлюз принял сообщение, — за упавшую отправку никто не платил. Сбой самой записи никогда не роняет доставку: сообщение уже у клиента, и потерянная строка учёта стоит меньше, чем доставленное сообщение, превращённое в ошибку.

`businessId` может быть пустым — это восстановление пароля, где у владельца может быть несколько бизнесов. В метрике такие попадают в `businessId="platform"`. При удалении бизнеса строки остаются с пустым `businessId`: ушедший салон не отменяет потраченных денег.

**Что тут не выдержит роста.** Две метрики размечены по `businessId` — SMS и клиенты, — потому что вопрос у них ровно про конкретный салон. Число серий растёт линейно с числом салонов: на пилоте это десятки строк, на сотнях салонов вывод станет нечитаемым руками, а Prometheus начнёт хранить лишнее. Порог, за которым per-business разметку надо выносить в отдельный отчёт, — примерно сотня активных салонов. Остальные метрики агрегатные и не растут.

Алерты об ошибках уходят в группу Telegram через платформенный бот; `PLATFORM_ADMIN_ALERT_CHAT_ID` на проде указывает на `-5018533849`. Бот обязан состоять в группе: `reportError` никогда не бросает исключение, поэтому неверный чат или бот вне группы выглядит как тишина — единственный след будет `observability.alert_failed` в логах.

## 7.3. Подтверждение телефона и восстановление пароля

Оба потока используют один код из SMS и включаются наличием одобренного payom-шаблона в `PAYOM_PHONE_VERIFICATION_TEMPLATE_ID`. Пока переменная пуста, публичная запись работает как раньше, а страница `/reset-password` честно сообщает, что восстановление недоступно.

Порядок включения:

1. Создайте в payom шаблон **«{text-1} - код подтверждения: {code-1}»** — сначала тот, кто спрашивает, потом код. Код обязан лежать в `code-1`: это типизированный placeholder payom для одноразовых кодов, и вариант с кодом в свободном `text-2` модерация отклоняет («Используйте соответствующие переменные»). Модерация занимает часы; отредактировать шаблон после создания нельзя, а расхождение с этим текстом отправит клиенту буквальное «{code-1}» вместо цифр.
2. Задайте `PAYOM_PHONE_VERIFICATION_TEMPLATE_ID` и оставьте `PHONE_VERIFICATION_REQUIRED=false`. Коды начнут отправляться, но незаверенная запись всё ещё пройдёт — сутки-двое смотрите долю подтверждений.
3. Переведите `PHONE_VERIFICATION_REQUIRED` в `true`. С этого момента `/api/bookings`, `/api/bookings/recurring` и `/api/public/waitlist` отвечают `403 VERIFICATION_REQUIRED` без подтверждённого номера, а форма записи сама показывает поле для кода.

Состояние на проде (07.08.2026): шаблон `df83ca2e-1405-45db-9762-f9398c529fe4` одобрен и прописан, `PHONE_VERIFICATION_REQUIRED=false` — то есть шаг 2 пройден, шаг 3 ждёт статистики по реальным клиентам. Отправка и приём кода проверены на живом проде.

`{text-1}` — это тот, кто спрашивает код: при записи и в листе ожидания название бизнеса, взятое **из базы по слагу** (строку из запроса не принимаем — иначе можно рассылать SMS, подписанные чужим салоном), при восстановлении пароля `ManClient`, потому что у владельца может быть несколько бизнесов и подписать код одним из них значило бы соврать. Название длиннее 40 символов усекается: кириллическая SMS вмещает 70 символов на сегмент, фиксированный текст съедает 28, и слишком длинное имя удваивало бы цену каждого кода.

Код живёт 10 минут, повторная отправка — не чаще раза в минуту, пять неверных попыток гасят код. Подтверждённый код одноразовый: одна SMS — одна запись. Записи, созданные в Telegram-боте бизнеса, подтверждения не требуют: владение номером там уже доказано чатом.

Восстановление пароля владельца: `/reset-password` → код на номер регистрации → новый пароль. Запрос по неизвестному номеру отвечает так же, как по известному, и SMS не отправляет. Успешная смена пароля попадает в audit log бизнеса как `auth.password_reset`.

## 7.3.1. Кабинет клиента

`/my` — страница, где клиент видит свои записи во всех салонах платформы сразу. Вход по номеру телефона: код в SMS, тот же механизм, что и подтверждение записи, но с назначением `CUSTOMER_LOGIN` — код от входа нельзя потратить на запись и наоборот. Пароля нет и не планируется.

Сессия — подписанная кука `manclient-customer` (HMAC на `AUTH_SECRET`), 60 дней, `httpOnly`. Серверной таблицы сессий нет: смена `AUTH_SECRET` разлогинивает всех, и это единственный рычаг массового отзыва.

Что это даёт в деньгах: клиент, вошедший один раз, при следующей записи **не тратит SMS на подтверждение номера** — сессия уже доказала владение. При 0,045 сомони за SMS один вход окупается со второй записи того же клиента.

Вход требует того же одобренного шаблона, что и §7.3. Пока `PAYOM_PHONE_VERIFICATION_TEMPLATE_ID` пуст, `/my` честно говорит, что вход недоступен, и предлагает написать салону.

Что клиент может со страницы: посмотреть ближайшие и последние 20 прошедших записей, перенести (та же ссылка, что даёт Telegram-бот) и отменить. Отмена подчиняется окну салона (`freeCancellationHours`) — «поздно» отвечает `409` и просит позвонить. Чужую запись достать нельзя: выборка идёт по номеру из сессии, ответ на чужой id — `404`, а не `403`, чтобы по разнице ответов нельзя было перебирать идентификаторы.

Ссылка «Мои записи» стоит в шапке публичной страницы салона. Там же работает автозаполнение: вошедшему клиенту имя и телефон подставляются сами.

## 7.4. Лимиты запросов

Счётчики лежат в PostgreSQL (`RateLimitCounter`), окна фиксированные, subject хранится хешем. Ограничены: создание записи (12 за 10 минут на IP и на номер), повторяющаяся запись, лист ожидания, проверка промокода (30 за 10 минут — иначе endpoint работает оракулом для перебора кодов), загрузка чека, запрос и проверка SMS-кода, вход (10 за 15 минут на аккаунт и на IP), регистрация и восстановление пароля. Превышение — `429` с `retry-after`.

Вход считается отдельно: лимит тратят только **неудачные** попытки, по аккаунту (10 за 15 минут) и по адресу (60 за 15 минут). Успешный вход счётчик не расходует — иначе смена персонала за одним NAT выбивала бы весь салон; ровно на это наткнулся браузерный сюит, логинясь демо-владельцем два десятка раз подряд.

Лимитер определяет клиента по первому значению `x-forwarded-for`, поэтому приложение обязано стоять за reverse proxy, который этот заголовок перезаписывает. При недоступности БД лимитер пропускает запрос и пишет `rate_limit.unavailable` уровня `error` — это состояние стоит алерта.

## 8. Ротация ключа карты

1. Сделайте backup БД и остановите запись новых/редактирование карт.
2. Передайте старый и новый ключ только через secret manager environment.
3. Запустите `pnpm db:rotate-card-key`.
4. Обновите `CARD_ENCRYPTION_KEY` новым значением и перезапустите приложение.
5. Проверьте генерацию ссылки по одному филиалу; затем удалите старый key из runtime secret set.

Скрипт не выводит номера карт. Если хотя бы одна расшифровка не удалась, transaction откатывается.

## 9. Release gate

Порядок production release:

1. Сделайте backup PostgreSQL и зафиксируйте текущий рабочий image/SHA.
2. Запустите `pnpm prisma migrate deploy`; миграция настроек добавляет поля и таблицы, не удаляя историю записей.
3. Разверните приложение из того же проверенного SHA.
4. Выполните health probe и owner smoke ниже.
5. Только после smoke регистрируйте или обновляйте webhooks.

```bash
pnpm prisma validate
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm playwright test
```

CI больше нет, и это осознанно. Пайплайн жил на GitHub Actions, оплата минут прекращена; попытка перенести выполнение на боевой сервер оказалась хуже болезни — один прогон съедал 6 ГБ диска и разгонял load average выше девяти на машине, которая обслуживает прод.

Что вместо него. Первые четыре команды выше запускает git-хук `.githooks/pre-push` — то есть проверки идут до пуша, на машине разработчика. Хук подключается один раз на клон:

```bash
git config core.hooksPath .githooks
```

Обойти можно (`git push --no-verify`), и это тоже осознанно: гейт, который нельзя открыть, обходят способами, которых никто не видит.

**Браузерный сюит в хук не входит** — он поднимает dev-сервер и добавляет минуты к каждому пушу. При этом он единственный проверяет продукт через браузер и ловит то, чего юнит-тесты не видят, поэтому перед значимым релизом его надо запускать руками: `pnpm test:e2e`.

Главное следствие, которое надо держать в голове: **пуш в `main` уезжает на прод сам.** Coolify подписан на репозиторий через GitHub App (`is_auto_deploy_enabled`), собирает и раскатывает без чьего-либо участия. Между `git push` и клиентами не осталось ни одной автоматической проверки, кроме сборки самого Coolify — а она ловит только то, что не компилируется. Упавшая сборка не роняет прод: старый контейнер продолжает отвечать, пока новый не станет здоровым, так что цена ошибки — устаревший прод, а не лежащий.

Подлинность входящих webhooks закрыта тестами: `tests/unit/security/webhook-auth.test.ts` (сравнение секрета и подписи) и `tests/integration/security/webhook-authentication.test.ts` (каждый endpoint отдельно). Главное, что они держат: **ненастроенный секрет закрывает webhook, а не открывает его**. Если `TELEGRAM_WEBHOOK_SECRET`, `WHATSAPP_APP_SECRET` или `WHATSAPP_VERIFY_TOKEN` не выставлены в окружении, endpoint отвечает 401/403 всем, включая пустой заголовок. Поэтому забытая переменная в Coolify ломает интеграцию заметно — вместо того чтобы тихо пустить внутрь любого, кто знает URL.

### HTTPS probe

```bash
pnpm probe:https -- --url https://manclient.mubi.dev --wait 180
```

Семь проверок по развёрнутому инстансу, exit code 1 при любом провале:

| Проверка | Что ловит |
| --- | --- |
| `https` | цель probe вообще по HTTPS — по http всё ниже пройдёт и не докажет ничего |
| `certificate` | сертификат живой и до конца больше 14 дней; продление идёт за 30, так что две недели молчания — это застрявший renewal, а не «ещё рано» |
| `no plaintext` | порт 80 редиректит на https или закрыт; cookie сессии помечены `Secure`, страница по 80-му порту переписывается сетью |
| `health` | `200 {"status":"ok"}` — заодно доказывает, что прод дотягивается до базы |
| `legacy webhook gone` | POST на `/api/webhooks/telegram` отвечает `410`; старый endpoint после cutover не должен принимать updates |
| `telegram webhook secret set` | POST без секрета получает `401` — значит `TELEGRAM_WEBHOOK_SECRET` в окружении есть |
| `whatsapp verify token set` | заведомо неверный `hub.verify_token` получает `403` — значит `WHATSAPP_VERIFY_TOKEN` есть и не пустой |

Последние две — это тот же контракт, что закрыт unit-тестами, но проверенный на живом окружении: тесты доказывают, что код без секрета закрывается, probe доказывает, что секрет вообще доехал до Coolify. Переменная, которую забыли добавить, выглядит как здоровое приложение ровно до первого входящего webhook.

`--wait N` повторяет весь набор, пока контейнер поднимается, но не дольше N секунд.

Оговорка про `certificate`: внутри окружения, которое терминирует TLS за вас (корпоративный прокси, sandbox egress gateway), probe видит сертификат прокси, а не тот, что отдаётся наружу. Запускайте с обычной сети.

Кто это запускает теперь. Раньше probe был последним шагом job `deploy`; job больше нет, и **автоматически после релиза не проверяет никто**. Coolify раскатывает по вебхуку и на этом успокаивается — здоровье контейнера он видит, а истёкший сертификат или потерянный `TELEGRAM_WEBHOOK_SECRET` нет. Поэтому после заметного релиза probe надо позвать руками, с `--wait`, чтобы дождаться подъёма нового контейнера.

`pnpm deploy:coolify` при этом никуда не делся и остаётся полезным: он не просто дёргает деплой, а **дожидается конца сборки** (endpoint триггера отвечает сразу после постановки в очередь). Нужен, когда деплой запускают не пушем — переменную окружения поменяли, или надо пересобрать тот же коммит.

**Сознательно отложено (13.08.2026):** репетиция восстановления из бэкапа и проверка, что S3-бакет не публичный. Решение владельца, зафиксировано здесь, чтобы не всплывало каждый релиз как забытое. Что это значит на практике: бэкапы Postgres снимаются (§7.0), но **ни разу не разворачивались** — то есть в момент аварии мы узнаем не только про потерю данных, но и про то, восстановим ли мы их вообще; а по бакету с чеками клиентов мы не знаем, отдаёт ли он объекты по прямой ссылке без подписи. Обе проверки — часовые, и делать их лучше до того, как они понадобятся.

### Owner smoke после release

1. Войти владельцем и открыть `Филиалы`, `Команда`, `Ресурсы`, `Услуги`, `Расписание`.
2. Создать временный черновик услуги, изменить его и архивировать. История существующих записей не должна исчезнуть.
3. Изменить часы будущего дня, открыть публичную запись и проверить соответствующий список слотов.
4. На ширине 390 px открыть нижнее меню `Ещё`, перейти в настройки и убедиться, что доступен выход.
5. На публичной странице выбрать филиал, опубликованную услугу, специалиста и свободное время.

### Smoke подписки

1. `Настройки → Тариф и оплата`: видны действующий тариф, статус и срок. У нового бизнеса это `Пробный период` с числом оставшихся дней.
2. Выбрать тариф и период — цена показывается до подтверждения; подтверждение называет тариф и сумму. После него появляется счёт с номером `SUB-…`, ссылкой на оплату (если задана `PLATFORM_PAYMENT_CARD`) и полем для чека.
3. Прислать чек: он либо закрывает счёт сразу, либо уходит в `Платформа → Подписки`, и кабинет говорит, что чек проверяет оператор.
4. В бэкофисе подтвердить или отклонить чек и убедиться, что срок в кабинете изменился, а в журнале бизнеса появилось событие.
5. Перевести бизнес в `GRACE` (`Тариф → Оплачено по` — вчерашняя дата, затем дождаться часовой задачи или запустить `pnpm jobs:subscriptions`): на любой странице кабинета появляется баннер с датой отключения, который закрывается на сессию.

### Smoke рабочего места записей

1. Открыть `Записи`: в режиме «День» должна отрисоваться сетка — колонка на специалиста, рабочие часы поверх закрытых, перерывы и буферы видны. Проверить «Список» и поиск по имени и телефону.
2. Переключить «Неделя»: семь колонок с общим окном часов, закрытые дни серые, клик по заголовку дня открывает этот день. Свободные получасы кликабельны только когда в филиале один специалист или один выбран в фильтре — иначе форма не знала бы, к кому записывать. Визит перетаскивается и здесь: по вертикали меняется время, по горизонтали — день; специалист остаётся тот же.
3. Если у бизнеса несколько филиалов, над сеткой появляются вкладки филиалов, и активная показывает, какой именно филиал нарисован. Список под сеткой ограничен тем же филиалом. Сотрудник без явного выбора попадает на свой филиал, а не на самый старый.
4. Перетащить визит в сетке дня на другое время (шаг 15 минут) и в колонку другого специалиста: время меняется, в истории записи появляется `booking.rescheduled` с прежним специалистом. Отпущенный визит сразу остаётся там, куда его положили, и над сеткой видно «Переносим запись…», пока сервер не ответил; отказ («специалист занят», «нельзя в прошлое») возвращает визит на место и объясняет причину. Перенос другому специалисту доступен владельцу и администратору; сотрудник переставляет только свои визиты по времени. Мышь не единственный путь — форма переноса в карточке записи работает как раньше.
5. Нажать `+` в свободном получасе: форма новой записи открывается с подставленными филиалом, специалистом, датой и временем; после выбора услуги слот уже выбран.
6. Создать ручную запись на свободное время. Она должна быть `Подтверждена`, источник `Создана в кабинете`, оплата `Не оплачено`.
7. Открыть карточку, перенести запись и убедиться, что старый слот освободился, а новое время появилось в истории.
8. Отменить запись с понятной причиной. Статус должен стать `Отменена`, напоминания перейти в `SKIPPED`, история сохраниться.
9. На записи с прошедшим временем нажать «Отметить неявку»: статус `Неявка`, счётчик у клиента вырос, напоминания `SKIPPED`.
10. Войти сотрудником: список и прямые URL должны показывать только записи этого специалиста.

### Smoke кабинета клиента

1. Открыть `/my` без куки: страница предлагает войти по номеру телефона. Пока SMS-шаблон не подключён, вместо кода должна быть честная строка «Вход по SMS пока недоступен».
2. Ввести номер, по которому в базе есть запись, и код из SMS. После входа видно имя салона, услугу, специалиста и время в часовом поясе филиала.
3. Отменить ближайшую запись: карточка спрашивает подтверждение, статус меняется на `Отменена`, запись уходит в «Прошедшие», а в кабинете салона слот освобождается.
4. Открыть страницу салона (`/b/<slug>`) той же кукой: имя и телефон подставлены, ссылка «Мои записи» есть в шапке.
5. Нажать «Выйти» и убедиться, что `/my` снова просит номер.

### Rollback приложения

Если smoke не проходит, остановите новые deploy, верните предыдущий проверенный image/SHA и повторите health probe. Не откатывайте additive migration и не удаляйте новые таблицы: старое приложение их игнорирует, а удаление уничтожит настройки расписаний и связей. Созданные во время smoke временные сущности архивируйте через кабинет после восстановления.
